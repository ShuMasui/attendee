## 1. 概要

本書は、ドメインモデルv1.1の図を、出欠管理システム(仮称)の要件定義書として書き起こしたものです。図から読み取れる内容と、要件にするために補った内容を分けて記載します。あわせて、2026年10月5日時点の進め方(フルスクラッチ開発・運用保守まで行う・スコープは本書の範囲に固定)を前提として反映しています。

### 1.1 目的

生徒が授業の開始時と途中に出欠確認を行い、その結果を先生と生徒がそれぞれ確認できるようにします。公欠は運用担当のオペレータが登録します。

### 1.2 記載ルール

- **【図】**: 図に描かれている内容をそのまま要件にしたもの
- **【補足】**: 図にはないが、要件として成立させるために補った内容。いずれも確認が必要です(9章)
- **【決定】**: 2026年10月5日時点で決まった方針。10章にまとめています

### 1.3 根拠資料

- ドメインモデルv1.1(先生・生徒・オペレータとシステムの間の10本のやり取りを描いた図)

### 1.4 開発・運用の前提【決定】

| ID | 前提 | 意味すること |
| --- | --- | --- |
| D-07 | フルスクラッチで開発する | 既存の出欠管理製品・パッケージを土台にせず、自分たちで設計・実装する。ただし認証は D-02 のとおり Amazon Cognito に任せる【補足】 |
| D-08 | 運用保守まで自分たちで行う | 開発して終わりにせず、リリース後の運用・保守も担う。必要な観点は7.2 |
| D-09 | スコープは本書の範囲に固定する | 取り組む範囲は2章のとおり。これ以外には取り組まない(2.3) |

## 2. スコープ

対象は、授業の出欠の記録・確認・参照と、そのために必要な本人確認、人・授業・公欠の登録です。

### 2.1 対象範囲

- 【図】先生と生徒の本人確認
- 【図】オペレータによる人・授業・公欠の登録
- 【図】先生による授業の登録
- 【図】生徒による授業開始時と授業途中の出欠確認
- 【図】先生への出席確認結果の提供
- 【図】生徒への自分の出席状況の提供
- 【決定】オペレータによる先生・生徒のアカウント作成(D-03)
- 【決定】ベンダーによるテナントの作成と、オペレータのシードアカウントの発行(D-05, D-06)
- 【決定】利用者が所属するテナントのデータだけを扱えること(D-06)

### 2.2 対象外【補足】

図に現れない以下の機能は、本書では対象外とします。必要な場合は追加で要件化します。

- 成績管理、履修登録、時間割の自動作成
- 保護者への通知
- 学籍・時間割など外部システムとの連携
- Microsoft SSOとの連携(MVP段階では行わない)【決定】

### 2.3 スコープの扱い【決定】(D-09)

- 取り組むのは2.1だけです。2.2と、本書に書かれていないものには取り組みません。
- 運用保守(D-08)は、2.1の機能を動かし続けるための作業に限ります。監視やバックアップのような運用のための仕組みは非機能要件(7.2)として扱い、利用者向けの機能は増やしません。
- 範囲外の要望が出たときは、本書に追記し、合意してから着手します。

## 3. アクター定義

図には、利用者として先生・生徒・オペレータの3者がおり、すべてが1つの「システム」とやり取りします。

| アクター | 役割 | 図で行うこと |
| --- | --- | --- |
| 先生 | 授業を担当し、出席状況を確認する | 自分を証明する / 授業を登録する / 出席確認の結果を受け取る |
| 生徒 | 授業を受け、出欠確認を行い、自分の出席状況を知る | 自分を証明する / 授業開始時と途中に出欠確認を行う / 自分の出席状況を受け取る |
| オペレータ | 人・授業・公欠をシステムに登録する運用担当 | 公欠・人・授業を登録する |
| ベンダー | システムの提供側。テナントを作成し、オペレータのシードアカウントを発行して渡す【決定】。本システムの開発・運用保守も担う想定【補足】 | 図には描かれていない(10章) |
| システム | 上記の入力を受けて記録し、結果を返す対象システム | 内部構成は図に描かれていない |

## 6. データ要件

図に登場する名詞と10章の方針から、システムが保持するデータの候補を5つ挙げます。属性は設計の出発点となる候補で、すべて【補足】です。

| エンティティ | 概要 | 属性の候補 | 関連する要件 |
| --- | --- | --- | --- |
| 人 | 先生・生徒・オペレータ | 氏名、メールアドレス、区分(先生/生徒/オペレータ)、所属テナント、Cognito上のユーザーとの対応づけ | FR-01〜04, 18〜22 |
| 授業 | 先生またはオペレータが登録する授業 | 授業名、担当の先生、日時、受講する生徒 | FR-05〜07 |

## 10. 決定事項・認証/テナントの設計方針

2026年10月5日時点の方針です。MVP段階ではMicrosoft SSOの申請を待たず、利用者をこちらで持ち、認証はAmazon Cognitoに任せます。この方針から、FR-18〜25の追加、Q-02の解決、Q-01の絞り込み、Q-12〜15の追加を行いました。あわせて、開発・運用の進め方(D-07〜D-09)を決め、Q-16〜18を追加しました。

### 10.1 決定事項【決定】

| ID | 決定事項 | 補足 |
| --- | --- | --- |
| D-01 | MVP段階ではMicrosoft SSOを使わず、利用者をこちらで持つ | SSOの申請に時間がかかるため |
| D-02 | 認証はすべてAmazon Cognitoに任せる | Cognitoの管理者によるユーザー作成の機能で、オペレータによる作成を実現できる |
| D-03 | オペレータが名前と属性から利用者を作成し、サインイン情報を本人に渡す | 渡し方はQ-15で確認 |
| D-04 | 同一人物の判断キーはメールアドレスとする | 将来Microsoft SSOに移るとき、既存の利用者と同一人物として結びつけるため |
| D-05 | オペレータの本人確認は、ベンダーが渡すシードアカウントで行う | シードアカウントはベンダーが事前に渡す |
| D-06 | 出席確認型のSaaSとして、マルチテナントを採用する | 採用する見込みという判断。構成はQ-14で確認 |

### 10.2 利用者作成の流れ【補足】

図の「人の登録」(UC-08)は、アカウントの作成を含む形で実現する想定です。

1. ベンダーがテナントを作成し、最初のオペレータとなるシードアカウントを渡す。
2. オペレータがシードアカウントでサインインし、初回のパスワードを自分のものに変える。
3. オペレータが先生・生徒の名前、メールアドレス、区分を入力して、アカウントを作成する。
4. システムがCognitoにユーザーを作成し、サインイン用の初期情報を本人へ渡せる状態にする。
5. 先生・生徒が初回サインインし、パスワードを自分のものに変える。

### 10.3 設計時の留意点【補足】

以下は提案で、決定ではありません。

- アプリのデータベースの主キーは、メールアドレスではなく、Cognitoのユーザー識別子(sub)か自前のIDにする。メールアドレスは変わりうるため、同一人物の照合にだけ使う。
- メールアドレスは、小文字にそろえて保存する。
- 先生・生徒・オペレータの区分は、カスタム属性ではなくCognitoのグループで持つ。カスタム属性は、作成後に削除や型の変更ができないため。
- オペレータにはCognitoの操作権限を持たせない。ユーザー作成はバックエンドが代行し、オペレータかどうかはアプリ側で判定する。
- 将来Microsoft SSOを足すときは、既存の利用者との結びつけにメールアドレスを使う。結びつける条件(ドメインや検証状態)は絞る。
